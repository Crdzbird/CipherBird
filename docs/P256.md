# P-256 ECDSA with SHA-256 (ES256)

`include/cryptolib/p256.hpp`, the `cryptolib_p256_*` functions of the C ABI,
and the Go, Dart and Node calls over them. This is the signature a JSON Web
Token carries as ES256 (RFC 7518) and the one Apple push authenticates a
provider with.

## What it is

| | |
|---|---|
| Secret key | 32 bytes, the scalar d big-endian, 1 <= d < n |
| Public key | 65 bytes, the uncompressed point `0x04 || X || Y` |
| Signature | 64 bytes, `r || s` big-endian (IEEE P1363, the JWS form) |
| Hash | SHA-256 of the message, computed inside the call |

Every curve operation runs in OpenSSL libcrypto: signing and verifying
through `EVP_DigestSign` and `EVP_DigestVerify`, the public point of a
scalar through `EC_POINT_mul`, the on-curve check of a public key through
`EVP_PKEY_public_check`. The library adds no curve arithmetic of its own;
its code marshals buffers, compares scalars with the group order in
constant time and reads the fixed PKCS#8 shape.

## Where it exists

The full and bank profiles. The functions never vanish from the ABI: where
libcrypto is absent or was configured without EC, `cryptolib_p256_available`
returns 0 and every call reports the feature as not enabled.

That is the case for every self-contained build: the engines bundled in
the Flutter plugin and the Dart package (Android, iOS, macOS), the
WebAssembly engine, and the sealed static archive of
`scripts/build_static_archive.sh` and its Linux twin. Their libcrypto is
built from `scripts/lib_openssl_trim.txt`, which configures `no-ec no-ecdsa`
(and `no-ecdh`) to keep the engine small. On devices P-256 is the
platform's own, through `DeviceFips`. Offering it from a self-contained
build means removing those options from the trim list and rebuilding, which
is a size and release decision and is not taken here; a server that signs
with P-256 and links the sealed static archive needs exactly that change.
A build against a stock OpenSSL (Homebrew, a distribution package, the
`build/release` library the Go binding links by default) has it.

The fips profile is unchanged: it keeps `cryptolib_fips_p256_*`, which stay
inside the validated module and return DER signatures.

## Decisions

**Raw signatures only, no DER form.** Every consumer this was written for
(JWS ES256, Apple push, WebCrypto, IEEE P1363) uses `r || s`. DER
signatures are where ECDSA parsers have historically gone wrong (non-minimal
integers, negative values, trailing data), so a second encoding would
double the parsing surface for no present caller. The fips layer already
speaks DER for those who need it there, and a strict converter can be added
later without touching these functions.

**Deterministic nonces (RFC 6979) where libcrypto has them.** OpenSSL 3.2
and later derive the nonce from the key and the digest when asked
(`nonce-type` 1). Signing then draws no randomness, so a weak or forked
random source cannot leak the key through a repeated nonce, and the RFC 6979
A.2.5 answers are reproduced byte for byte, which makes signing testable
against a published answer. The library asks for it and fails rather than
fall back if the request is refused. Against an older libcrypto the code
compiles to libcrypto's default nonce, which mixes the private key and the
digest into its random draw; `cryptolib_p256_available` returns 2 for
deterministic and 1 otherwise. The pinned OpenSSL of the sealed builds
(3.6) and current Homebrew are both deterministic.

**High-s signatures are produced and accepted.** FIPS 186-5 and JWS do not
normalise s, RFC 6979 fixes the nonce and not the half of the range, and
Go's `crypto/ecdsa`, CryptoKit and WebCrypto emit both halves; refusing
high s would refuse about half of their signatures. A P-256 signature is
therefore malleable: `(r, n - s)` verifies too, and a signature must never
serve as a unique identifier. secp256k1 in this library enforces low s
because the EVM and Bitcoin rules require it; that rule does not exist for
P-256.

**Verification is strict about form.** A signature must be exactly 64
bytes with r and s in 1..n-1; a public key must be exactly 65 bytes,
uncompressed, with coordinates below the field prime and on the curve.
Compressed and hybrid points are refused.

**Key generation uses the library's CSPRNG.** The scalar is drawn from
libsodium's `randombytes_buf` by rejection (FIPS 186-5 A.2.2) and the
public point derived from it, so the library has one random source in
every profile that carries P-256.

**PKCS#8 import is a strict reader of one shape.** `PrivateKeyInfo`
(RFC 5208) around `ECPrivateKey` (RFC 5915), which is what `openssl
genpkey`, Go's `x509.MarshalPKCS8PrivateKey` and an Apple `.p8` file hold.
The reader is written against that shape instead of handed to a general
decoder, so what it accepts is exactly what is listed. Refused, each with
its own message: trailing bytes, a bare SEC 1 ECPrivateKey, a PKCS#8
version other than 0, an
algorithm other than id-ecPublicKey, a curve other than prime256v1 (in the
algorithm identifier or in the key's own parameters), attributes, an
EncryptedPrivateKeyInfo, an ECPrivateKey version other than 1, a scalar
that is not exactly 32 bytes or not in 1..n-1, an embedded public key that
is not the uncompressed point of that scalar, and any indefinite or
non-minimal DER length. Input is capped at 4096 bytes. The PEM form takes
one block labelled `PRIVATE KEY` with only whitespace around it and a
padded base64 body; `ENCRYPTED PRIVATE KEY` and `EC PRIVATE KEY` blocks are
refused by name. The public key returned is always derived from the scalar,
never copied from the file. The scalar lives in a `SecureBuffer`, the
decoded PEM body too, and the C buffer handed back is zeroed by
`cryptolib_buffer_free`.

## API

C ABI (`bridge/cryptolib_c.h`):

```c
int cryptolib_p256_available(void);
CryptoKeyPair cryptolib_p256_keygen(void);
CryptoBufferResult cryptolib_p256_public_key(const uint8_t* secret_key, size_t sk_len);
CryptoBufferResult cryptolib_p256_sign(const uint8_t* secret_key, size_t sk_len,
                                       const uint8_t* message, size_t msg_len);
int cryptolib_p256_verify(const uint8_t* public_key, size_t pk_len,
                          const uint8_t* message, size_t msg_len,
                          const uint8_t* signature, size_t sig_len);
CryptoBufferResult cryptolib_p256_import_pkcs8_der(const uint8_t* der, size_t der_len);
CryptoBufferResult cryptolib_p256_import_pkcs8_pem(const uint8_t* pem, size_t pem_len);
```

The two importers return 97 bytes: the secret key (32) followed by its
public key (65).

| | Go | Dart | Node |
|---|---|---|---|
| availability | `P256Available`, `P256DeterministicNonces` | `p256Available`, `p256DeterministicNonces` | `p256Available`, `p256DeterministicNonces` |
| keys | `P256GenerateKey`, `P256PublicKey` | `p256GenerateKey`, `p256PublicKey` | `p256GenerateKey`, `p256PublicKey` |
| sign, verify | `P256Sign`, `P256Verify` | `p256Sign`, `p256Verify` | `p256Sign`, `p256Verify` |
| import | `P256PrivateKeyFromPKCS8`, `P256PrivateKeyFromPEM` | `p256PrivateKeyFromPkcs8`, `p256PrivateKeyFromPem` | `p256PrivateKeyFromPkcs8`, `p256PrivateKeyFromPem` |

An ES256 JWT in Go:

```go
key, err := cryptolib.P256PrivateKeyFromPEM(p8File)
signingInput := b64(header) + "." + b64(claims)
signature, err := cryptolib.P256Sign(key.Secret, []byte(signingInput))
token := signingInput + "." + base64.RawURLEncoding.EncodeToString(signature)
```

## Tests

`tests/vectors/p256/ecdsa_p256_sha256.json` is written by
`scripts/p256/convert_vectors.py` from the NIST CAVP archive
`186-4ecdsatestvectors.zip` (the P-256 cases of KeyPair.rsp and PKV.rsp,
the P-256 and SHA-256 cases of SigVer.rsp and SigGen.txt) and from RFC 6979
appendix A.2.5. The repository does not vendor Wycheproof; its
`ecdsa_secp256r1_sha256_p1363` file would be a good addition for more
malformed-signature cases.

- C++ (`tests/test_p256.cpp`): the vectors; the generator for d = 1; the
  edges of the scalar range; every form of non-canonical signature and
  public key; keys the OpenSSL command line wrote, in DER and PEM; every
  single-bit flip and every truncation of such a key refused; one refusal
  per rule of the importer. Runs in the full, bank and sanitizer builds.
- Go (`p256_test.go`): the vectors, and a cross-check against the Go
  standard library in both directions: `crypto/ecdsa` verifies what
  cryptolib signs and cryptolib verifies what `crypto/ecdsa` signs (both
  halves of the s range), and keys written by `crypto/x509` import to the
  same scalar and point.
- Dart and Node: the vectors, round trips and the import rules; Node also
  cross-checks against `node:crypto`.
