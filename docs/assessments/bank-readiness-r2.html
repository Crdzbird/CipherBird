CryptoLib engine and CipherBird bindings

Commit af56e56 (main) Packages cipherbird 1.1.2, cipherbird_dart 1.1.2 Engine CryptoLib 3.0.0 Assessed 2026-10-18 Supersedes revision 1 (d3bbf60, 2026-10-15)
EXECUTIVE VERDICT
NO-GO, with real progress

Since revision 1 the two reproduced memory-safety bugs are fixed and regression-tested. The shipped mobile and web engines moved to libsodium 1.0.22 and OpenSSL 3.5.9 LTS, and CI is green for the first time. One critical and two high findings are closed, and one of the two critical findings that remain depends on a decision the bank still has to make. Reasons it is still NO-GO:

  1. Shipped binaries still have no verifiable provenance. All 10 native blobs on pub.dev were built on the maintainer's workstation. The only SLSA provenance covers a desktop dylib nobody ships, and release tags v1.1.1 and v1.1.2 were re-pointed after release (9 and 2 commits respectively).
  2. No FIPS 140-3 validated module. This is unchanged. It is critical if the bank requires validation, which US banks and most PCI assessors expect, and high otherwise.
  3. Keys can still leak at the edges. Bindings still free key and password copies without wiping them, and no binding uses Secure Enclave or StrongBox. The new web boot path accepts any page script's object as the crypto engine.

Closest path to GO WITH CONDITIONS: build and attest every shipped blob in CI, and make release tags immutable (C1, N1). After that, the verdict rests on the bank's FIPS answer and on the binding hygiene work.

2. Scope and frame

The scope is unchanged from revision 1: EU, US and UK frames at their strictest intersection; PCI cardholder data, SCA credentials, PII and transaction integrity; assurance target unknown, so FIPS-dependent findings carry both readings; all platforms. Materials added in this revision:

  • The 22-commit diff d3bbf60..af56e56, including the new PublicBuffer output type and the WebAssembly randomness provider.
  • The published pub.dev 1.1.2 archives, downloaded and compared with git HEAD.
  • The GitHub release objects and the Release workflow history.
Still not reviewed: internals of BBS, FROST, OPAQUE, OPRF and ECVRF; the steganography subsystem; Swift, Python, Ruby and Rust bindings in depth; constant-time measurement (no Linux or ctgrind job yet); and the consuming banking app.

3. Open findings

Critical

C1CRITICALEvery shipped native binary is still built outside any pipelineSUPPLY
Evidence
  • The 10 blobs are the Android arm64 and x86_64 .so, iOS device and simulator, the macOS framework, cipherbird.wasm and .js in both packages, and the Dart desktop dylib.
  • All carry workstation paths (/Users/crdzbird/CLionProjects/cryptolib/build/...) or Homebrew paths.
  • release.yml builds only libcryptolib_c.dylib.
  • The pub.dev 1.1.2 archives are byte-identical to git HEAD, which is good. That proves only that what was committed got published, not what it was built from.
Frame
PCI DSS 4.0.1 Req 6.3.2; DORA ICT third-party risk; SLSA build integrity.
Remediation
A CI matrix (macOS runner for Apple slices, Linux runner with a pinned NDK and Emscripten for Android and wasm) builds every slice from hash-pinned sources and attests each one. Publishing then fails unless each committed blob's sha256 equals its attested subject.
Verify
Run slsa-verifier verify-artifact on each blob extracted from the pub.dev archive.
C3CRITICAL*No FIPS 140-3 validated module or approved modeGAP
Evidence
Unchanged from revision 1: no OSSL_PROVIDER_load, no fips=yes, no power-on self-tests, and libsodium defaults. The new mobile and web OpenSSL 3.5.9 is the line currently in CMVP review (3.5.4 submitted); it is not validated, and the sealed desktop build still uses no-dso.
Impact
*CRITICAL if the bank requires a validated module; HIGH otherwise.
Remediation
A FIPS profile through an already-validated module per platform: the OpenSSL 3.1.2 FIPS provider (certificate #4985) on servers, and the platform modules on iOS and Android. This is engineering work, not a certification of CryptoLib itself.

High

N1HIGHRelease tags were re-pointed after release; provenance attests a file users never receiveSUPPLYNEW
Evidence
  • Moved tags: the Release workflow ran for v1.1.1 on 9 commits (fc3a755 to 7c5ff2a) and for v1.1.2 on 2 (4c5b547, then 0e5636c). 9 stale draft releases remain.
  • Release contents: the v1.1.2 release holds one asset, libcryptolib_c.dylib.intoto.jsonl. The attested dylib (sha256 fa1a9ba2...) is not attached and matches no shipped binary.
  • Ephemeral artifacts: the SBOM appears only on drafts. The cosign signature lives only in a workflow artifact, which expires 2027-01-16.
  • No CI gate: Release ran green on 4c5b547 while CI on the same commit was red.
Impact
A bank cannot tie "version 1.1.2" to one commit. Two consumers who fetched the tag at different times may hold different code, and both see a provenance file that names neither.
Remediation
  • Make tags immutable: a GitHub tag ruleset forbidding update and delete, plus signed annotated tags.
  • Never re-use a version; ship a new patch version instead.
  • Attach the shipped blobs, SBOM, SHA256SUMS, .sig and .pem to the release.
  • Make Release depend on a green CI run for the same SHA, and delete the stale drafts.
H9HIGHEngine substitution at load time, now worse on the webSUPPLYLEAK
Evidence
  • New web boot path: adoptPageEngine() takes whatever object is at self.cipherbirdEngine as the crypto engine, with no check (platform/web/page_engine.dart:10-16). It runs before anything else, even when the caller passed an explicit library URL (engine_loader.dart:23).
  • Other trusted globals: an existing cipherbirdEnginePromise or createCipherBird global is trusted the same way (engine_loader.dart:48-55,78-86).
  • No integrity checks: web_setup writes the engine script tags without integrity. The worker blob still interpolates base into script text (engine_worker.dart:19-21).
  • Native overrides unchanged: CIPHERBIRD_LIBRARY and CRYPTOLIB_DYLIB, cwd search, the JVM temp extract.
Impact
On the web, any script that runs earlier on the page supplies the entire crypto engine and sees every key: a third-party tag or an XSS payload. Bank web apps commonly carry analytics and tag-manager scripts.
Remediation
Only adopt an engine the library itself created, using a module-scoped reference, never a page global. Add SRI hashes to the web_setup tags and to importScripts. Pass base to the worker with postMessage. Remove the native env-var and cwd overrides from release builds.
H3HIGHBindings leave keys and passwords in unwiped memoryLEAK
Evidence
Unchanged:
  • Dart: marshal_buffers.dart:40-47 frees calloc memory without wiping. Passphrases go through toNativeUtf8. The KEM shared secret is never wiped (easy/kem_key_pair.dart:48-49). There is a SymmetricKey.destroy(), but it zeroes only one Dart heap copy.
  • Go: plain C.free (cryptolib.go:165-180,692,752,796-814,856).
  • JVM: one Arena per instance.
  • Web worker: _free without zeroing.
  • Node, Python, Ruby, Rust, .NET, Swift: no wipe calls found.
Remediation
Wipe before every free. Use zeroizing secret handles. Pass passwords as bytes. On JVM, use one arena per call.
H4HIGHNo hardware-backed key generation, storage or attestationKEYMGMT
Evidence
Unchanged. Keystore and Keychain code exist only as samples outside the shipped plugin.
Frame
PSD2 RTS on SCA (Delegated Regulation (EU) 2018/389), possession element.
Remediation
Hardware-first key API: Secure Enclave P-256 and Keystore with StrongBox, biometric gating, attestation. The hardware key wraps the Keyring master.
H5HIGHPlatform dependency downloads still unhashed; blst unpinned outside CISUPPLY
Evidence
  • fetch_tarball in scripts/{ios,android,web}/lib/common.sh is atomic now but checks no sha256.
  • The shipped blobs carry three different blst snapshots: Android dece82e, iOS 4f72b30, and CI v0.3.17 54e6e55.
  • The NDK is "newest installed", and Emscripten and Homebrew versions float.
Remediation
Record a sha256 per tarball and refuse to build on mismatch, following the pattern in build_openssl_nosock.sh. Use install_blst.sh on every platform. Pin the NDK and Emscripten versions in the scripts and in the SBOM.
H7HIGHNo working vulnerability disclosure channelMAINT
Evidence
No SECURITY.md. The README now tells reporters to use GitHub Security Advisories, but private-vulnerability-reporting returns {"enabled":false}, so that route does not work. There is no supported-versions policy.
Remediation
Enable private reporting (one setting), add SECURITY.md with a contact and response targets, and publish supported versions.
H8HIGHSingle maintainer, no review controls, no external auditMAINT
Evidence
main is unprotected with no rulesets. 0 of the last 20 commits are signed, and the v1.1.1 and v1.1.2 tags are unsigned. There is one author, and the README still lists the external audit as pending.
Remediation
Branch protection with required CI and review; signed commits and tags; the independent audit scoped in the audit-options note; an exit plan for the bank's DORA register.

New code reviewed and found sound

  • PublicBuffer split: no internal path puts secret-derived data into a plain buffer. The four internal Digest callers hash public data, every decrypt path still returns SecureBuffer, keyed BLAKE2b and BLAKE3 stay secret, and cryptolib_buffer_free still wipes every C ABI output.
  • WebAssembly randomness: crypto.getRandomValues is called per buffer in 64 KiB chunks (cryptolib_c.cpp:216-251). It is installed before sodium_init, with no user-space generator in between. If the browser API is missing, it fails closed with an exception rather than weak bytes. liboqs draws from getentropy, which maps to the same source.
  • Integrity of what was published: the pub.dev 1.1.2 archives match git HEAD exactly, and the committed OpenSSL 3.5.9 and libsodium 1.0.22 tarballs match upstream checksums.

5. Roadmap to GO WITH CONDITIONS

Phase 0 done

Parser fixes with regression tests, dependency upgrades on mobile and web, green CI. Verified in this revision.

Phase 1: provable releases and quick wins C1, N1, H5, H7, H9, N2, N3

  • Quick wins first, about an hour each: enable private vulnerability reporting, add SECURITY.md, protect main, add a tag ruleset that blocks tag updates, delete the stale drafts, and fix cryptolib_init's return code.
  • Build all 10 shipped slices in CI from hash-pinned sources (blst through install_blst.sh everywhere). Attach the blobs, SBOM and signatures to the release, and gate publishing on hash equality.
  • Remove the web page-global adoption path, add SRI, and drop the native env-var overrides in release builds.
  • Build the Dart desktop dylib from the sealed OpenSSL and unify versions across slices.

Phase 2: binding hygiene and hardware keys H3, H4, M1, M2

  • Wipe-before-free in every binding; zeroizing handles; passwords as bytes.
  • Hardware-first key API with attestation for the SCA possession factor.
  • Close the core zeroization gaps and cap Argon2 parameters.

Phase 3: regulated production C3, H8, M4-M9

  • FIPS profile on validated modules; external audit of the bank profile; bank build without stego and non-standard combiners.
Audit timing: Phase 1 should land before an external auditor starts. Otherwise the audit spends billed days rediscovering the provenance and disclosure gaps above, which you can close yourself.
