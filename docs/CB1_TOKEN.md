# cb1: CipherBird tokens, version 1

cb1 is CipherBird's own token format. It keeps the shape, the grammar and
the security argument of PASETO version 4 and swaps in this library's
primitives: BLAKE3 where v4 uses BLAKE2b, and the Ed25519 + ML-DSA-65
hybrid signature where v4.public uses Ed25519. It is not PASETO. A PASETO
parser rejects a cb1 token by its header, and the cb1 functions reject
PASETO tokens the same way, so the two formats never pass for each other.

The conformant PASETO v4.local lives beside it, byte for byte the PASETO
specification and checked against the official vectors. Use v4.local where
another PASETO implementation has to read the token; use cb1 where both ends
run CipherBird and you want the post-quantum signature or the faster hash.

## Grammar

```
token   = version "." purpose "." payload [ "." footer ]
version = "cb1"
purpose = "local" | "public"
payload = base64url(body)        ; unpadded, RFC 4648 section 5
footer  = base64url(f)           ; omitted when f is empty
```

Base64url is strict on input: only the 64 URL-safe characters, no padding,
no length of 1 mod 4, and the unused low bits of the last character must be
zero, so every byte string has exactly one accepted encoding. A token that
carries a footer when none is expected, or none when one is, is invalid.

PAE is the pre-authentication encoding of PASETO: the count of pieces as a
64-bit little-endian integer with the top bit clear, then each piece as its
length in the same encoding followed by its bytes.

## cb1.local

Inputs: a 32-byte key K, a message m, a footer f (may be empty) and an
implicit assertion i (may be empty; authenticated, never stored).

```
h        = "cb1.local."
n        = 32 random bytes from the CSPRNG
Ek || n2 = BLAKE3-keyed(K, "cb1-encryption-key" || n), 56 bytes of output
Ak       = BLAKE3-keyed(K, "cb1-auth-key" || n), 32 bytes
c        = XChaCha20(Ek, n2) XOR m
t        = BLAKE3-keyed(Ak, PAE(h, n, c, f, i)), 32 bytes
body     = n || c || t
```

Decryption checks the header, decodes the body and the footer, compares the
footer with the expected one, recomputes t and compares it in constant time,
and only then decrypts. Every failure that depends on the token returns one
verdict, invalid, with no further detail.

The construction is Encrypt-then-MAC with keys derived per token from K and
n. Because Ak is derived from K, the tag commits the ciphertext to the key: a
token cannot open under a second key, which closes the partitioning-oracle
class of attacks against non-committing authenticated encryption. The 56-byte
extendable output of keyed BLAKE3 is the keyed mode of the BLAKE3
specification, a pseudorandom function; the 32-byte tag is a MAC in the same
mode. XChaCha20 with a 24-byte nonce carries the message, as in v4.local.

Limits: the message, footer and implicit assertion are each at most 2^26
bytes. Nonces are drawn from a per-thread batch filled by the system CSPRNG
and discarded in a forked child, as for v4.local.

## cb1.public

Inputs: a hybrid secret key sk (4096 bytes: Ed25519 64 || ML-DSA-65 4032),
the matching public key pk (1984 bytes: Ed25519 32 || ML-DSA-65 1952), a
message m, a footer f and an implicit assertion i.

```
h    = "cb1.public."
m2   = PAE(h, m, f, i)
sig  = Ed25519-sign(sk_ed, m2) || ML-DSA-65-sign(sk_mldsa, m2), 3373 bytes
body = m || sig
```

Verification splits the last 3373 bytes of the body as the signature,
rebuilds m2 from the message, the expected footer and the implicit
assertion, and accepts only if both halves verify. A forgery therefore needs
a break of both Ed25519 and ML-DSA-65 (FIPS 204, security category 3). The
message travels in clear; the token is a signed statement, not a secret.

## Keys

cb1.local keys are 32 uniformly random bytes; `symKeygen` or any 32-byte
output of a key derivation serves. cb1.public keys are the pairs that
`hybridSigKeygen` produces in every binding. Keys are raw bytes and the API
cannot tell a local key from a public key by type: callers keep them apart.

## Profiles

cb1 is library-native, so it follows the policy of the other library-native
constructions: present in the full profile, absent from the bank profile
(the functions exist there and report `CRYPTOLIB_PASETO_ERR_UNAVAILABLE`,
-4, so a full-profile client still links), and absent from the fips profile
like every libsodium-backed function. PASETO v4.local is a published
standard and is in the bank profile.

## Vectors

`tests/vectors/cb1/vectors.json` holds tokens generated by the C++ suite
from this description, with a fixed key and nonce for the local vectors
(regenerate with a `CRYPTOLIB_PASETO_TEST_NONCE=ON` build and
`CRYPTOLIB_CB1_WRITE_VECTORS=1`) and a fixed hybrid key pair for the public
ones. The C++, Go, Dart and Node suites all decrypt and verify them, and the
C++ suite also re-encrypts the local vectors with the pinned nonce and
compares byte for byte, and checks both constructions against an
independent re-implementation written from this document.

## API

The C ABI (`bridge/cryptolib_c.h`) exposes `cryptolib_cb1_local_encrypt_len`,
`cryptolib_cb1_local_decrypt_cap`, `cryptolib_cb1_local_encrypt`,
`cryptolib_cb1_local_decrypt`, `cryptolib_cb1_public_sign_len`,
`cryptolib_cb1_public_verify_cap`, `cryptolib_cb1_public_sign` and
`cryptolib_cb1_public_verify`, with the calling convention and return codes
of the PASETO v4.local functions: tokens into caller buffers, no allocation
on the local path, 0 for success and negative codes for invalid, argument,
internal and unavailable.

| Binding | Local | Public |
|---|---|---|
| Go | `Cb1LocalEncrypt`, `Cb1LocalDecrypt`, `Cb1LocalDecryptTo` | `Cb1PublicSign`, `Cb1PublicVerify`, `Cb1PublicVerifyTo` |
| Dart (both packages) | `cb1LocalEncrypt`, `cb1LocalDecrypt`, `lib.tokens` | `cb1PublicSign`, `cb1PublicVerify` |
| Node | `cb1LocalEncrypt`, `cb1LocalDecrypt`, `Cb1`, `tokens` | `cb1PublicSign`, `cb1PublicVerify` |
